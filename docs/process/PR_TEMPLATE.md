# PR Template

[Назад в README](../../README.md)

## Зачем
Этот шаблон нужен, чтобы pull request был понятен reviewer'у без устного сопровождения.

Если PR нельзя нормально описать этим шаблоном, скорее всего:

- задача была плохо понята;
- изменение слишком большое;
- автор сам до конца не понимает, что сделал.

## Шаблон PR

### 1. Что сделано
Короткий список конкретных изменений.

Формат:
- добавил ...
- изменил ...
- убрал ...

Пример:
- добавил вычисление stale projects в attention service;
- обновил `GET /today`;
- показал stale section на web Today screen.

### 2. Зачем это сделано
Один короткий абзац про смысл.

Пример:
`Это нужно, чтобы пользователь видел проекты без движения и не терял их из внимания.`

### 3. Что не входит в этот PR
Очень важный раздел.

Пример:
- не менял mobile;
- не делал сортировку stale projects;
- не рефакторил attention module целиком.

### 4. Как проверить
Пошаговая проверка.

Пример:
1. Создать active project.
2. Поставить `last_activity_at` старше 7 дней.
3. Открыть Today.
4. Убедиться, что проект появился в stale section.

Если есть тесты:
- какие тесты запущены;
- что они покрывают.

### 5. Риски / спорные места
Что reviewer должен проверить особенно внимательно.

Пример:
- логика stale сейчас считается только для active проектов;
- blocked проекты не попадают в stale section.

### 6. Скриншоты / примеры ответа API
Если PR меняет UI или API, нужно приложить:

- скриншот;
- или пример JSON;
- или короткое описание diff в поведении.

## Мини-чек перед открытием PR
Перед созданием PR автор должен проверить:

- [ ] я сам перечитал свой diff;
- [ ] я убрал лишние файлы и случайные изменения;
- [ ] я понимаю, как работает мое изменение;
- [ ] я написал, как это проверять;
- [ ] reviewer сможет понять PR без звонка со мной.

## Когда PR не готов
PR не готов к review, если:

- в описании написано только `fix` или `done`;
- автор сам не проверил изменение;
- PR содержит несколько независимых задач;
- автор не может объяснить, что проверять.
