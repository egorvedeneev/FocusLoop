# Code Review Checklist

[Назад в README](../../README.md)

## Зачем
Этот чеклист нужен, чтобы review был не формальным, а полезным. Он особенно важен для команды, которая еще учится читать код.

## Как использовать
Reviewer не обязан писать комментарий по каждому пункту. Но он обязан пройтись по этим вопросам в голове.

## 1. Понял ли я, что делает PR
- Понятна ли цель изменения?
- Понятно ли, зачем это изменение вообще нужно?
- Можно ли пересказать суть PR в 2-3 предложениях?

Если нет, сначала просим автора улучшить описание PR.

## 2. Решает ли PR нужную задачу
- Изменение действительно закрывает заявленную проблему?
- Нет ли расхождения между задачей и реализацией?
- Нет ли лишнего кода, который не относится к задаче?

## 3. Безопасно ли изменение
- Может ли это сломать соседние сценарии?
- Нет ли подозрительных изменений в существующей логике?
- Не нарушаются ли важные доменные правила?

Для этого проекта особенно проверять:

- у active проекта не пропал ли `next action`;
- корректно ли обрабатывается blocked / follow-up;
- не ломается ли логика `Today`;
- не расходится ли web/mobile поведение.

## 4. Понятен ли код
- Можно ли понять код без устного объяснения автора?
- Хорошо ли названы функции, переменные и методы?
- Нет ли избыточно сложных конструкций там, где можно проще?
- Есть ли дублирование?

Если решение сложно читать, это уже проблема, даже если оно работает.

## 5. Следует ли изменение архитектуре
- Логика лежит там, где ей положено?
- Не уехали ли бизнес-правила во frontend без причины?
- Не нарушается ли agreed architecture из `ARCHITECTURE.md`?

## 6. Хороший ли размер PR
- PR не слишком большой?
- Его реально прочитать и проверить за разумное время?
- Нет ли нескольких независимых изменений в одном PR?

Если PR слишком большой, лучше попросить разделить.

## 7. Проверил ли автор свой код
- Есть ли описание проверки?
- Понятно ли, как это тестировалось?
- Есть ли хотя бы ручной сценарий проверки?

## 8. Нужно ли менять документацию
- Меняется ли поведение продукта?
- Меняется ли API?
- Меняется ли архитектурное решение?

Если да, reviewer должен спросить, обновлены ли документы.

## Как писать замечания
Хорошее замечание:

- конкретное;
- короткое;
- проверяемое;
- объясняет риск.

Плохое замечание:

- расплывчатое;
- вкусовое без причины;
- без объяснения, что именно не так.

## Примеры хороших замечаний
- `Здесь active project может остаться без next action. Это ломает наше доменное правило.`
- `Эта функция делает сразу 3 вещи, ее трудно читать и проверять.`
- `Не понял, почему эта логика живет во frontend, а не в backend service.`
- `В PR не описано, как проверить новый сценарий block/unblock.`

## Когда approve не нужен
Не нужно ставить approve, если:

- reviewer не понял решение;
- reviewer видит риск, но надеется, что “наверное нормально”;
- автор не объяснил, как проверял изменение;
- PR слишком сырой.

## Что должен помнить reviewer
- Цель review не “доказать умность”.
- Цель review не “найти как можно больше замечаний”.
- Цель review — помочь команде держать код понятным и безопасным.

## Быстрый финальный чек
Перед approve reviewer должен суметь честно ответить `да` на 5 вопросов:

1. Я понимаю, что изменилось.
2. Я понимаю, зачем это сделано.
3. Я не вижу явного нарушения бизнес-логики.
4. Код можно читать без автора рядом.
5. Я понимаю, как это проверить.
