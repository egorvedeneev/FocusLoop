# Team Guidelines

[Назад в README](../../README.md)

## Зачем это нужно
Команда небольшая, продукт новый, а часть участников еще учится читать и писать production-like код. Эти правила нужны не для бюрократии, а чтобы:

- не ломать друг другу работу;
- делать изменения маленькими и понятными;
- быстрее замечать ошибки;
- учиться на общем процессе, а не на хаосе.

## Главные принципы
- Делать маленькие изменения.
- Сначала понять задачу, потом писать код.
- Если не понимаешь код, не угадывай.
- Любое нетривиальное решение надо уметь объяснить словами.
- Код должен быть читаемым для следующего человека, а не только для автора.

## Как мы работаем
Каждая задача проходит одинаковый путь:

1. Понять, что именно нужно сделать.
2. Найти, где это живет в коде.
3. Прочитать существующую реализацию рядом.
4. Сформулировать план изменения в 3-5 пунктах.
5. Сделать минимальное изменение.
6. Проверить вручную и, если есть, тестами.
7. Описать изменения в PR простыми словами.

## Обязательные правила для разработчика
- Не начинать кодить, если не можешь одним абзацем объяснить задачу.
- Не менять больше, чем нужно для текущей задачи.
- Не смешивать в одном PR рефакторинг и новую функциональность без явной причины.
- Не копировать код без понимания, что он делает.
- Не оставлять “магические” решения без объяснения.

## Если разработчик не понимает код
Нормальное поведение:

1. Сказать, что непонятно.
2. Выписать 3 вопроса:
   - где вход в логику;
   - где меняется состояние;
   - где формируется результат.
3. Прочитать соседние файлы и похожие места.
4. Только потом идти за помощью.

Неправильное поведение:

- менять код наугад;
- дублировать существующую логику;
- “попробую, вдруг заработает”.

## Размер задач
Для нашей команды задача считается хорошей, если ее можно:

- понять за 10-15 минут;
- реализовать за несколько часов или максимум за 1 день;
- проверить без долгой ручной экспедиции по проекту.

Если задача слишком большая, ее нужно делить.

## Размер PR
Хороший PR:

- решает одну задачу;
- имеет понятное название;
- читается за 10-20 минут;
- не содержит случайных файлов и мусорных изменений.

Плохой PR:

- “сделал сразу все”;
- 20 разных идей в одном месте;
- невозможно понять, что именно было изменено.

## Что важнее скорости
Для этой команды важнее:

- понятность;
- повторяемость процесса;
- предсказуемость;
- обучение читать существующий код.

Скорость вырастет потом, если сначала вырастет качество процесса.

## Definition of Done
Задача считается сделанной, если:

- понятно, что именно изменено;
- изменение работает в нужном сценарии;
- не сломаны очевидные соседние сценарии;
- код не выглядит как временный хаос;
- PR можно прочитать и понять без устного сопровождения.

## Коммуникация
- Лучше задать короткий точный вопрос, чем молча делать неверно.
- Лучше заранее показать промежуточный план, чем потом объяснять большой неправильный PR.
- Если решение спорное, обсуждаем до merge, а не после.

## Главное правило
Если решение нельзя понятно объяснить словами, скорее всего команда пока недостаточно его поняла.
