# Development Workflow

[Назад в README](../../README.md)

## Цель
Этот документ описывает простой и обязательный workflow разработки для команды.

## Короткая версия
Поток работы по задаче:

1. Прочитать задачу.
2. Уточнить непонятное.
3. Найти затронутые файлы.
4. Прочитать текущую реализацию.
5. Составить короткий план.
6. Сделать изменение.
7. Самостоятельно проверить.
8. Открыть PR.
9. Исправить замечания.
10. Слить только после понятного review.

## Шаг 1. Понять задачу
Перед началом разработки автор задачи должен ответить на 4 вопроса:

- Что должно измениться для пользователя?
- Где это, скорее всего, живет в системе?
- Какой минимальный результат нужен в этой задаче?
- Как мы поймем, что задача сделана?

Если на эти вопросы нет ответа, задача еще не готова к разработке.

## Шаг 2. Исследовать код
Перед изменением кода разработчик должен:

- найти главный вход в нужную логику;
- найти связанные файлы;
- прочитать хотя бы один похожий пример в кодовой базе;
- выписать, где данные приходят, где меняются и где уходят.

Минимум перед изменением:

- не меньше 2-3 связанных файлов прочитать внимательно;
- понять, есть ли уже похожая реализация;
- проверить, нет ли конфликта с архитектурными документами.

## Шаг 3. Написать мини-план
Перед началом кодинга разработчик пишет мини-план в 3-5 пунктов.

Пример:

1. Добавить поле в модель.
2. Обновить API schema.
3. Изменить обработчик на backend.
4. Подключить изменение в UI.
5. Проверить сценарий вручную.

Если план не формулируется, значит задача еще недостаточно понятна.

## Шаг 4. Реализация
Правила реализации:

- менять только нужные файлы;
- не делать “попутный” рефакторинг без договоренности;
- не трогать стиль и форматирование в несвязанных местах;
- не выдумывать абстракции заранее.

Если видно архитектурную проблему:

- зафиксировать ее отдельно;
- не пытаться чинить весь мир в рамках текущей задачи.

## Шаг 5. Самопроверка
Перед PR разработчик обязан сделать self-review.

Нужно проверить:

- не остались ли debug-кусочки;
- нет ли лишних файлов;
- понятны ли названия переменных и функций;
- нет ли очевидного дублирования;
- совпадает ли реализация с задачей.

## Шаг 6. Проверка сценария
Каждый PR должен содержать краткую проверку:

- что проверялось;
- как проверялось;
- какой сценарий теперь работает.

Минимальный формат:

- `Проверил создание проекта`
- `Проверил block/unblock`
- `Проверил, что Today показывает новый state`

Если тесты есть, запускаем тесты. Если тестов нет, описываем ручную проверку.

## Шаг 7. Pull Request
Каждый PR должен содержать:

- краткое название;
- что изменено;
- зачем изменено;
- как проверить;
- что осталось вне scope.

Хороший шаблон описания PR:

```text
Что сделано:
- ...

Зачем:
- ...

Как проверить:
- ...

Не входит в этот PR:
- ...
```

## Шаг 8. Review
PR не должен сливаться без review.

Reviewer смотрит на:

- понятность решения;
- корректность логики;
- соответствие задаче;
- читаемость кода;
- риски сломать соседние сценарии.

## Когда нужно звать на помощь раньше
Не надо сидеть слишком долго молча.

Нужно звать помощь, если:

- 30-40 минут не удается понять, где менять код;
- нашлось слишком много связанных мест;
- неясно, это баг или задуманное поведение;
- решение получается слишком большим.

## Чего мы не делаем
- Не коммитим “черновики”, которые автор сам не проверял.
- Не открываем PR с сообщением “посмотрите, вроде работает”.
- Не мерджим код, который автор не может объяснить.
- Не используем PR как способ впервые понять собственное изменение.

## Definition of Ready
Задача готова к разработке, если:

- понятна пользовательская цель;
- понятен минимум результата;
- есть хотя бы грубое понимание затронутых мест;
- есть критерий приемки.

## Definition of Done
Задача сделана, если:

- код работает в нужном сценарии;
- изменение проверено;
- PR понятен reviewer'у;
- замечания обработаны;
- документация обновлена, если это было нужно.
