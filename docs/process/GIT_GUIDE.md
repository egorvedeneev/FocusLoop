# Git Guide

[Назад в README](../../README.md)

## Зачем это нужно
Этот документ нужен как базовая инструкция по `git` для команды, где не у всех есть опыт работы с кодом и репозиториями.

Главная цель:

- не ломать общую ветку;
- не терять свои изменения;
- делать понятную историю работы;
- спокойно работать в команде из нескольких человек.

## Что такое Git простыми словами
- `repository` — папка проекта с историей изменений.
- `commit` — сохраненная точка в истории.
- `branch` — отдельная ветка работы под свою задачу.
- `push` — отправить свои изменения на сервер.
- `pull` — забрать свежие изменения с сервера.
- `pull request` — запрос на добавление своей ветки в общую ветку `main`.

## Главное правило команды
Не работаем напрямую в `main`.

Правильный путь всегда такой:

1. Забрать свежий `main`.
2. Создать отдельную ветку под задачу.
3. Сделать небольшое изменение.
4. Сохранить его в `commit`.
5. Отправить ветку на сервер.
6. Создать `pull request`.
7. Слить изменения только после review.

## Как называть ветки
Используем короткие и понятные имена:

- `feature/login-page`
- `feature/create-project`
- `fix/inbox-validation`
- `docs/update-readme`

Если у задачи есть номер, можно так:

- `feature/12-create-project`
- `fix/27-header-bug`

## Ежедневный сценарий работы
Перед началом задачи:

```bash
git checkout main
git pull
git checkout -b feature/my-task
```

Что происходит:

- переходим в основную ветку;
- забираем свежие изменения;
- создаем новую ветку под задачу.

Во время работы полезно смотреть состояние репозитория:

```bash
git status
```

Когда задача готова:

```bash
git add .
git commit -m "Add project creation form"
git push -u origin feature/my-task
```

Что происходит:

- `git add .` подготавливает изменения к коммиту;
- `git commit` сохраняет изменения в историю;
- `git push` отправляет ветку в удаленный репозиторий.

## Как писать commit message
Сообщение коммита должно быть коротким и понятным.

Хорошие примеры:

- `Add login page layout`
- `Fix project status validation`
- `Update architecture documentation`

Плохие примеры:

- `fix`
- `changes`
- `123`
- `something`

## Что делать, если `main` изменился
Пока вы работали, кто-то мог уже обновить `main`.

Тогда обновляем свою ветку так:

```bash
git checkout main
git pull
git checkout feature/my-task
git merge main
```

Если появился конфликт, это значит, что два человека изменили одно и то же место в коде.

Тогда нужно:

1. Открыть конфликтный файл.
2. Выбрать правильный вариант кода.
3. Удалить служебные метки конфликта.
4. Сохранить файл.
5. Выполнить:

```bash
git add .
git commit -m "Resolve merge conflict"
```

Если непонятно, как решать конфликт, лучше позвать того, кто менял код раньше, и разобрать это вместе.

## Pull request
`Pull request` нужен, чтобы изменения попали в `main` через проверку, а не напрямую.

Перед PR проверьте:

- проект запускается;
- вы не сломали соседний сценарий;
- в коммите нет случайных файлов;
- название ветки и описание понятны.

В описании PR достаточно написать:

- что сделано;
- зачем это нужно;
- как это проверить.

## Чего нельзя делать
- Не коммитить сразу в `main`.
- Не смешивать несколько разных задач в одном коммите.
- Не загружать в репозиторий пароли, токены и другие секреты.
- Не делать огромные коммиты "сразу со всем".
- Не менять чужой код наугад.

## Минимальный набор команд
```bash
git status
git pull
git checkout main
git checkout -b feature/my-task
git add .
git commit -m "Short clear message"
git push -u origin feature/my-task
git merge main
```

## Самое безопасное правило для нашей команды
Если сомневаетесь, действуйте так:

1. Сначала `git pull`.
2. Потом новая ветка под одну задачу.
3. Потом маленький понятный `commit`.
4. Потом `push` и `pull request`.

Это самый безопасный сценарий для начинающей команды.
