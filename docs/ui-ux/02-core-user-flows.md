# Основные пользовательские сценарии

[Назад в README](../../README.md)

## Сценарий 1: Утренний вход в «Сегодня»
### Намерение пользователя
Начать день с чёткого понимания того, что требует внимания прямо сейчас.

### Точки входа
- запуск приложения
- утреннее напоминание
- возвращение после бездействия

### Основная цель интерфейса
Снизить неоднозначность и предложить следующий полезный шаг менее чем за 5 секунд.

### Сценарий в вебе
1. Пользователь попадает на экран `Сегодня`.
2. В заголовке показываются дата, текущая сводка внимания и действие `Быстрый захват`.
3. Первая панель показывает `Требует внимания сейчас`.
4. Пользователь просматривает три ранжированные секции:
   - просроченные фоллоуапы;
   - активные проекты без следующего действия;
   - рекомендуемые следующие действия.
5. Пользователь либо открывает проект, либо начинает фоллоуап, либо переходит к уточнению входящих.

### Сценарий на мобильном
1. Пользователь открывает приложение на экране `Сегодня`.
2. Верхняя карточка суммирует: `3 вещи требуют внимания`.
3. Лента показывает блоки, расположенные друг под другом в порядке приоритета.
4. Пользователь нажимает на один блок и сразу попадает на экран действия.

### UX-заметки
- При первой загрузке не показывать сырой бэклог.
- Каждый элемент внимания должен объяснять, почему он показан.
- Количество рекомендуемых действий должно быть ограничено, чтобы избежать перегрузки.

## Сценарий 2: Уточнение входящих
### Намерение пользователя
Преобразовать неструктурированный вход в структурированный и применимый результат.

### Точки входа
- вкладка `Входящие`
- всплывающее подтверждение захвата
- подсказка в `Сегодня` с текстом `Ожидают 5 элементов во входящих`

### Основная цель интерфейса
Уточнить один элемент через короткий и простой поток принятия решения с низким трением.

### Возможные результаты уточнения
- создать новый проект
- добавить следующее действие в существующий проект
- создать заблокированный фоллоуап
- прикрепить только к справочнику
- отклонить или архивировать

### Сценарий в вебе
1. Пользователь открывает `Входящие`.
2. Левая колонка показывает очередь элементов в порядке приоритета.
3. Выбор элемента открывает панель уточнения справа.
4. Панель задаёт вопрос: `Что это?`
5. Пользователь выбирает результат.
6. Форма динамически меняется:
   - при создании проекта запрашиваются название проекта и первое следующее действие;
   - при добавлении задачи запрашиваются целевой проект и текст действия;
   - в заблокированном потоке запрашиваются блокер, ответственный, дата возврата и действие фоллоуапа;
   - для справочника запрашиваются тип сущности и заголовок.
7. Сохранение удаляет элемент и автоматически переводит к следующей карточке входящих.

### Сценарий на мобильном
1. Пользователь открывает `Входящие`.
2. За раз показывается одна карточка.
3. Пользователь нажимает один из вариантов уточнения.
4. Появляется короткая полноэкранная форма.
5. После сохранения въезжает следующая карточка входящих.

### UX-заметки
- Уточнение по дизайну является последовательным.
- Не стоит показывать все поля сразу.
- Следующий элемент должен появляться мгновенно, чтобы сохранять ритм.

## Сценарий 3: Работа с проектом
### Намерение пользователя
Увидеть текущее состояние проекта и либо продвинуть его вперёд, либо обновить статус.

### Точки входа
- `Проекты`
- рекомендации в `Сегодня`
- поиск / уведомление / глубокая ссылка

### Основная цель интерфейса
Сделать следующее действие главным объектом на экране.

### Сценарий в вебе
1. Пользователь открывает `Проекты`.
2. По умолчанию показываются активные проекты.
3. Клик по проекту открывает его детали в контекстной панели.
4. Верхняя секция показывает:
   - название проекта;
   - бейдж статуса;
   - текущее следующее действие;
   - время последнего движения.
5. Основные действия:
   - `Завершить следующее действие`
   - `Изменить следующее действие`
   - `Заблокировать проект`
6. Вторичный контент показывает журнал активности, заметки и связанные сущности.

### Сценарий на мобильном
1. Пользователь открывает `Проекты`.
2. Вкладки или сегментированные контролы переключают между `Активные`, `Заблокированные` и `Завершённые`.
3. Нажатие на проект открывает отдельный экран деталей.
4. Карточка следующего действия находится наверху.
5. Быстрые действия закреплены ближе к нижней части экрана.

### UX-заметки
- Если у активного проекта нет следующего действия, состояние отсутствия заменяет обычную верхнюю карточку.
- Экран должен ощущаться как рабочий инструмент, а не как документ.

## Сценарий 4: Заблокированный фоллоуап
### Намерение пользователя
Безопасно поставить проект на паузу и гарантировать, что он вернётся, когда это потребуется.

### Точки входа
- действие `Заблокировать проект` внутри деталей проекта
- поток уточнения, когда элемент входящих превращается в ожидающую работу
- напоминание о просроченном фоллоуапе

### Основная цель интерфейса
Не дать заблокированной работе исчезнуть, сохранив сам поток блокировки лёгким.

### Поток блокировки
1. Пользователь инициирует `Заблокировать проект`.
2. Система открывает сфокусированную панель.
3. Пользователь должен указать:
   - описание блокера;
   - кто или что блокирует;
   - дату возврата.
4. Пользователь опционально может задать:
   - отправленное сообщение;
   - ожидаемый результат;
   - текст следующего действия фоллоуапа.
5. Сохранение меняет статус проекта на `Заблокирован`.
6. Проект уходит из активного представления и появляется в `Фоллоуапах`.

### Поток возврата
1. В выбранную дату проект появляется в `Сегодня` и `Фоллоуапах`.
2. Система помечает его как `Вернулся сегодня`.
3. Основное действие:
   - `Отправить фоллоуап`
   - или `Вернуть в активные`
4. Если пользователь напомнил о себе и снова должен ждать, он может повторно заблокировать проект в одно нажатие.

### UX-заметки
- Проект всегда должен помнить, почему он был заблокирован.
- Путь возврата должен быть очевидным и ориентированным на действие.

## Сценарий 5: Еженедельный обзор
### Намерение пользователя
Понять недельный прогресс на уровне проектов и решить, куда перенаправить фокус дальше.

### Точки входа
- запланированное еженедельное напоминание
- вкладка `Обзор`
- баннер в `Сегодня`, если обзор просрочен

### Основная цель интерфейса
Суммировать движение, застой и риски, не превращая экран в перегруженную аналитику.

### Сценарий в вебе
1. Пользователь открывает `Еженедельный обзор`.
2. Вверху показываются выбранная неделя и короткая сводка:
   - проектов с движением;
   - отправленных фоллоуапов;
   - застопорившихся проектов.
3. Основная область разделена на сгруппированные секции:
   - продвинулись вперёд;
   - всё ещё заблокированы;
   - без движения;
   - нет следующего действия.
4. Клик по проекту открывает боковую краткую сводку деталей.
5. Пользователь может создать следующее действие или оставить заметку о перефокусировке прямо с экрана обзора.

### Сценарий на мобильном
1. Пользователь открывает `Обзор`.
2. Экран разбит на секции, расположенные друг под другом, или на короткий пошаговый сценарий:
   - успехи;
   - заблокированные;
   - устаревшие;
   - сбросить следующие действия.
3. Пользователь обрабатывает по одной секции за раз.

### UX-заметки
- Обзор должен подчёркивать движение проектов, а не считать каждую закрытую задачу.
- Экран обзора должен позволять лёгкое вмешательство, а не заставлять уходить с него ради каждого исправления.

## Общий паттерн микрокопии
- `Требует внимания, потому что...`
- `Следующий шаг`
- `Ожидаем`
- `Вернётся`
- `Нет следующего действия`
- `Нет движения 7 дней`
- `Уточнить этот ввод`

## Метрики успеха сценариев
- Утренний вход: первый осмысленный клик менее чем за 10 секунд
- Уточнение входящих: структурированный результат за 3 шага или меньше
- Работа с проектом: следующее действие видно без прокрутки
- Блокировка: невозможно потерять дату возврата
- Еженедельный обзор: пользователь может определить застопорившиеся проекты, не открывая каждый по отдельности
